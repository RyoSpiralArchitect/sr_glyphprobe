## 目的と範囲

絵文字を置き換えると、通常のベース言語モデルが二つの固定した自然言語の評価文に与える
相対確率は変わるか。その置換効果は、二つの文脈で異なるかを調べる。文脈間では明示された
目的を反転させる。多くの項目は、その目的と、絵文字が示すと考えられる状態との適合性を
調べる。**絵文字そのものの意味が変わる必要はない**。一定の手がかりを、文脈に応じて
応答へ結び付ける処理でも、予想した交互作用は生じ得る。

[24組の刺激](../data/contextual_emoji_development_v0.jsonl)は、この開発パイロット用に
英語で作成した。CLDRラベル、過去のターゲット集合、モデル出力の好みに基づいていない。
新しい文を作っても、新しい絵文字や事前学習に未露出のホールドアウトになるわけではない。
自然な絵文字利用や人間集団を代表するシナリオだとは主張しない。

| ファミリー | 四つの場面 | 絵文字の組 | 未解決の解釈 |
| --- | --- | --- | --- |
| 温度の目的 | 飲み物、スープ、部屋、タオル | 🔥 / 🧊 | 火は温かさだけでなく、強さ、良さ、危険を表す可能性がある。 |
| 音の目的 | スピーカー、電話、展示、動画 | 🔊 / 🔇 | 操作部は現在の状態ではなく次の動作を表示することがあり、通知音とメディア音も異なり得る。 |
| 完了状態の目的 | 印刷、発送、エクスポート、予約 | ✅ / ⏳ | チェックは完了ではなく受付を示すことがあり、保留中でも変更・取消が可能とは限らない。 |
| 感情表現の目的 | 演技、描画、絵コンテ、人形 | 😊 / 😢 | 笑顔が悲しみを隠し、涙が喜びを表すこともある。人手による二値の正解はない。 |
| 方向の目的 | エレベーター、カメラ、棚、舞台台 | ⬆️ / ⬇️ | 方向だけで到着先、移動量、安全な実行までは保証されない。 |
| 天候の目的 | 洗濯／雨水タンク、撮影、機器試験、柵／庭 | ☀️ / 🌧️ | 適合性は継続時間などにも依存するが、短いプロンプトには含めていない。 |

24組すべてに `design_status: author_defined_development` と
`interpretation_status: unvalidated_author_defined` を付け、各組に
`uncertainty_note` を記録する。ファミリーは六つであり、独立に妥当性が確認された
意味現象が24個あるわけではない。絵文字とテンプレートはファミリー内で再利用する。
取得された場合の通常出力の証拠も、この有限の項目群に限定される。

## 交差入力と候補文

各組は、一つだけ `{emoji}` スロットを持つ `context_p` と `context_q`、
`emoji_a` と `emoji_b`、全入力で共通の `candidate_a` と `candidate_b` を持つ。
各スロットに二つの絵文字を入れると四つの交差プロンプトになる。空文字列を入れると、
絵文字なしのプロンプトが二つできる。空白を示す特別な記号は挿入しない。ただしメッセージが
空になること自体は見えるため、絵文字なし対照にはこの不自然さが残る。

例えば、一方の文脈では体を温める飲み物、他方では冷やす飲み物を求め、カフェからの
メッセージに火または氷が入る。四つの条件すべてで、同じ肯定・否定の評価文を採点する。
これは解釈の仮案であって、人やモデルが支持したという意味ではない。

プロンプト末尾は `Mira's assessment:` のような通常の文章の続きを促す形式にする。
A/B選択肢の一覧、チャット命令、systemロール、チャットテンプレートは付けない。
候補文の先頭スペースと末尾の句読点は文字列に含める。自由生成ではなく、与えた続きの
確率を採点する teacher forcing である。

採点ラベルの整理として、各ファミリーの1・3番では肯定評価をA、2・4番ではBにする。
意図した対応は `orientation`、符号は `eta`（+1または−1）に記録する。A/Bラベルとetaを
同時に反転させても、Hは数式上変わらない。候補は別々に採点し、順序付き一覧として
モデルに提示しないため、これは提示順序のカウンターバランスではなく、肯定・否定・長さの
偏りを統制するものでもない。ファミリー内の四つの場面には異なる文面を用いるが、
一組あたりの候補ペアは一つ（`J = 1`）。文面への頑健性は推定しておらず、それぞれの
効果がその一組に依存する可能性がある。

## 採点と解釈

候補文の**全トークン**について、通常の対数確率を自然対数単位で合計する。
結果を見てから長さで正規化したり、先頭トークンだけを使ったり、有利な候補を選んだり、
EOSを追加したりしない。プロンプトと候補を連結してトークン化し、プロンプトがその
厳密なトークン接頭辞になっていることを確認する。境界検査に失敗したセルは失敗として
記録し、黙って別のトークン化へ切り替えない。

```text
s(c,e)  = log P(candidate_a | c,e) - log P(candidate_b | c,e)
Delta_p = s(context_p,emoji_b) - s(context_p,emoji_a)
Delta_q = s(context_q,emoji_b) - s(context_q,emoji_a)
H       = eta * (Delta_q - Delta_p)
```

四つの `s`、両delta、H、絵文字なしの両スコアをすべて報告する。Hが正なら作成者の
想定方向の交互作用があるが、効果の反転まで保証するわけではない。
`eta * Delta_p < 0` かつ `eta * Delta_q > 0` かを別の診断として報告する。
この診断だけが、想定した絵文字効果の方向反転を確認する。どちらも人間にとっての意味の
正解ラベルではない。

候補全文の対数確率には長さや文面による偏りがある。同じ文字列を交差条件間で使うと、
単純に加算される候補の好みは交互作用の式から消えるが、文脈に依存する語彙や
トークン化の効果までなくなるわけではない。候補トークン数、絵文字部分のトークン数と
位置、四つのスコアを残す。ベースラインではトークン数・位置の不一致があっても項目を残す。
将来の経路交換に必要な適格性規則は、別途、出力を見ずに定め、除外された項目数も明示する。

要約には全項目の効果、六つのファミリー平均、それらの等重み平均を示す。
最初のパイロットでは、ブートストラップ、p値、成功閾値、統計的な確認判定、母集団への
一般化を伴う区間は規定しない。正・ゼロ・負の値も、不確かな例も残す。セルが失敗すれば
その組は不完全とし、残ったセルやファミリーだけで黙って平均を作らない。

| 非絵文字の記号 | 今回の実行には割り当てない | 0 | 計画のみ。**未実施**。意味対応と中立的な凡例の設計は未解決 |
| K/V交換などの因果介入 | 0 | 0 | このプロトコルでは実装も実行もしない |
| **最初のパイロットの総割当** | **144** | **288** | **24組、六つのファミリー** |

通常単語は、トークン数や人間の解釈が一致する対照だとは主張しない。記号対照の
`+` と `-` は暫定的な候補にすぎず、妥当性のある意味対応や実行準備の整った課題ではない。
将来の設計では、明示的な凡例を与えること自体が課題を変える点を扱う必要がある。
どちらの対照も実施済みとして数えてはならない。これらがないため、このパイロットから
絵文字特異性や一般的な情報伝達手段に対する優位性は主張できない。

## モデル、取得前の条件、記録の保持

[設定ファイル](../configs/contextual_emoji_output_pilot_v0.json)には、以前使用した
Llama 3.2 3B base BF16のミラーとリビジョン
`60a99aaf43164077157d64bf909b7b61143c6a6d` を指定する。ダウンロード、生成、学習、
経路介入は許可しない。入力は以前のベースモデル設定に合わせ、特殊トークン・BOSを追加せず、
EOSも採点せず、チャットテンプレートも使わない。この選択は測定条件の一部であり、
どのベースモデル用プロンプト方式も同等だという主張ではない。

設定では、[同じリビジョンのT21モデル固定値](../configs/t21_glyph_context_path_pilot_v0.yaml)から
引き継いだアーティファクト・マニフェストのSHA-256
`dc5b61a2c4aa123f82e7d0471b4cdb3a7d8de3b6a8db327047fb1b6d05e3bdf4` も必須とする。
トークナイザーやモデルを読み込む前に、ローカルの実スナップショットがこの指定値と
一致しなければならない。渡された任意のスナップショットのハッシュを記録するだけでは不十分である。

GPUで計算する前に、親タスクが改訂PDFを確認し、モデル出力を見ない独立した刺激批評を
終え、刺激のハッシュを固定する。その後、runnerの準備記録が、実在する既存の
スナップショット、モデル／トークナイザーのファイル、実行環境、入力ハッシュを結び付ける。
設定内のスナップショット・実行環境欄は未確定のまま残し、書かれたパスやバージョンを
確認済みと装わない。計算資源が空いていることと、実装の事前検査も実行条件に含む。

入力ハッシュを固定する前に、別のエージェントが刺激を読み取り専用で批評した。
向きの符号の整合性を確認し、不確かな組もすべて残した。これは設計の点検であり、
独立した人によるアノテーションや意味的妥当性の確認ではない。この批評を受け、
採点ラベルの整理と、実際の提示順序のカウンターバランスを明確に区別した。

割当は候補文セル最大288、各プロンプトと候補を連結した全文で最大512トークン、
その内数として候補最大64トークン、実時間上限900秒とする。これは完了を保証する値ではない。準備、トークン境界、
資源の空き、時間制限で失敗した場合も、計画・完了・失敗のセル数と不完全な組を残す。
モデル出力を見てからシナリオを差し替えたり、有利な変種を未露出のように再実行したり
しない。後の開発用改訂では、この版を保持したうえで変更理由を説明する。

## このパイロットの後に判断できること

不正なプロンプト、トークナイザーの不整合、絵文字なし条件による支配、J = 1のため
未測定のまま残る候補文面への依存、弱い・一貫しない目的適合性の交互作用を確認する。
動作が正しく好ましい結果でも、得られるのは開発段階の実装・出力上の実行可能性に限られる。

より広い主張には、`ambiguous`、`both`、`neither` を選べる独立した人手評価、
別の候補文面、一般的な情報伝達手段による対照、別途凍結する新しいファミリーでの
確認実験が残る。通常状態からの双方向K/V交換は、独自の校正と対照を必要とする
後続の実装・実験である。その因果的な結論を、この出力だけのベースラインから導いてはならない。
