# 候補の形状をそろえ、全開発データを再評価する

[English](CONTEXTUAL_EMOJI_MATCHED_SHAPE_V1.md) · [8入力の診断結果](CONTEXTUAL_EMOJI_PREFIX_CONSISTENCY_RESULTS_V0.ja.md) · [研究の順序](CONTEXTUAL_EMOJI_MEASUREMENT_NEXT_PLAN_V0.ja.md)

2026-10-10（JST）。8入力の診断を受け、ユーザーが既存スコア全体の再評価を承認した。以下は新しいモデル出力を得る前に定めた仕様である。採点時の実行形状を別版にし、過去のスコアをすべて保持する。課題、候補文、人のラベル、モデル、因果介入は追加しない。

## 問いと対象

両候補を同じ実行形状・正規化形状で採点したとき、目標と手がかりの交互作用、効果の反転、候補選好はどれだけ変わるか。

対象は著者定義の開発用24課題・6課題群に属する、既存の全記録である。新しい確認用標本ではない。同じ手がかり、課題群、文脈、候補の言い換えを独立課題として数えない。

| 既存の取得元 | sequence score数 | 候補を比較する入力組 |
| --- | ---: | ---: |
| 元のemoji条件、手がかりなしを含む | 288 | 144 |
| 元の単語対照 | 192 | 96 |
| 追加した2組の候補文、両carrier | 768 | 384 |
| 合計 | **1,248** | **624** |

うち1,152スコアは手がかりあり576入力組、残る96スコアは元の候補文に対する手がかりなし48入力組である。手がかりなしは共有の対照であり、単語用に重複取得しない。追加した2組の候補文には手がかりなしの192スコアが存在せず、今回も取得しない。手がかりあり144ブロックは、それぞれ課題・carrier・候補組を固定した4入力（2文脈×2手がかり）からなる。

## 採点の別版

保存済みの結合prompt／candidate token IDをそのまま使う。tokenizer、BOS/EOSの追加、chat templateの変更、長さ正規化、文章生成、意味ラベルの変更は行わない。

各入力組で、2候補の全文token長の大きい方まで右側をtoken ID 0で埋める。実tokenのattention maskを1、paddingを0とし、絶対位置IDを明示する。モデルは固定済みLlama 3.2 3BのBF16・eager attention、評価／inferenceモード、KV cacheなしを保つ。

共通の予測領域 `[prompt_length − 1 : common_total_length − 1]` をFP32で正規化し、その後で有効な候補tokenの対数確率を取り出す。paddingを総和に含めない。tokenごとのスコア、総和、形状、共通接頭列を予測するfloat32 logitsのdigest・shapeを保存する。前回8入力で検査した採点経路と同じである。ただし、FP32相当の絶対精度や、emojiと単語prompt間のtoken・位置の同等性を確立するものではない。

前回の移植可能なCPU参照記録と過去の主要runtime全体を固定する。旧解析と、端末固有の補助的CPU演算差を保持する。runtime変更を通すためにモデルスコアの一致条件を緩めない。

## 実行数と順序

1. **開始時の再現検査32回。** 前回と同じ8入力それぞれで、元条件A、元条件B、padding条件A、padding条件Bの順に実行する。
2. **全記録1,248回。** 624識別子 `(pair, carrier, block, context, cue)` を辞書順に並べ、padding条件A、Bの順に採点する。手がかりなしのcarrierは `shared_absent` と明示する。
3. **終了時の再現検査32回。** 開始時と同じ順序を繰り返す。

失敗した試行も含め、最大 **1,312 forward**。実装確認の64回は再評価対象1,248スコアの分母に含めない。実行時間上限は900秒とし、自動再試行、途中再開、精度変更によるfallback、追加取得を行わない。

## 整合性と停止の条件

- 固定したソース、仕様、モデルファイル、過去のraw、前回の診断記録、主要runtime全体を、採点前に照合する。インストール済みの `modeling_llama.py` と `masking_utils.py` のSHA-256も、初回forward前に前回診断の実装記録と比較する。新しいhashを記録するだけでは不十分である。
- 元条件の再現検査では、tokenスコアと総和が過去と完全一致し、共通接頭列のlogit digestも前回診断と一致することを求める。padding条件のスコア・digestも前回値と完全一致させる。終了時は開始時とも一致を求める。全対象の中でこの8組と重なる16回の採点も、追加実行せずに過去・開始時と完全一致することを確認する。不一致なら許容差を広げず取得を止める。
- 全624組で、共通接頭列のtoken対数確率と、予測logitsのdigest・shapeの完全一致を求める。数値上の不一致は保持し、再現・資源条件が有効なら上限内で全対象を収集する。失敗例を差し替えたり、通過例だけで全体を報告したりしない。
- 各forwardの前後に、その実行IDと対応づけた占有記録を残す。他のGPU PID、占有情報の取得不能、空き不足、時間超過、自分のメモリ上限超過を検出したら、自分の取得だけを止める。
- 停止後も予定した全IDを残し、未実行／失敗を明示する。取得完了、数値一致、runtime・再現性、資源条件、解析への採用可否を分ける。欠けた検査を成功に数えない。
- 確保前は空き12,288 MiB以上、forward境界では4,096 MiB以上を求める。PyTorch allocator上限9,728 MiB、driver分512 MiBとする。空きを得るために他プロセスを変更しない。観測間の競合は排除できない。
- 新規runディレクトリへ排他的に保存し、過去や途中停止の記録を上書きしない。

未完了・不合格runは診断には使えるが、開発結果を置き換えることはできない。完全な新旧比較では、両版の対象全体を同じにする。

## 実行前に定める記述的比較

候補全文の対数確率総和を使い、`s(c,v) = log P(A | c,v) − log P(B | c,v)` とする。課題の著者定義方向 `eta` は保持する。

- 手がかり効果：`delta_p = eta [s(p,b) − s(p,a)]`、`delta_q = eta [s(q,b) − s(q,a)]`。
- 交互作用：`H = delta_q − delta_p`。正・0・負を分けて報告する。
- 効果の反転：`delta_p < 0 < delta_q`。
- 入力の著者方向margin：`eta × C × V × s`。`C(p/q) = −1/+1`、`V(a/b) = −1/+1`。正なら著者ラベルとの一致であり、人の正答率ではない。
- 全4条件一致：4つのmarginがすべて厳密に正。同点を別に残す。

独立したCPU解析で全記録を検証し、入力別・144ブロック別の新旧値、候補組／carrier別H集計、H符号・反転・絶対選好・全4条件一致の全遷移、token・全文スコアの差、候補組を跨ぐ安定性を出す。選好は手がかりあり576入力と手がかりなし48入力を分ける。元の候補組だけにある手がかりなし相対量も保持するが、差し引きを補正とは呼ばず、手がかりなしをHに混ぜない。

決定的な記述的再測定であり、p値、新たな推論用効果下限、同等性閾値、有利な候補組の選別は導入しない。形状をそろえた出力は、旧版と併記する別の採点版として扱う。
