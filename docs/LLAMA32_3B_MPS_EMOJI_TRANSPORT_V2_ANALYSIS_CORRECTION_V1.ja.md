## 操作者の申告に基づくインシデント記録

以下に記す 2 回の分析失敗の詳細は、操作者の申告に基づく。失敗時のコマンド、端末ログ、時刻を保存したハッシュには、暗号学的に結び付いていない。一方、完了済みの実行レシートと元のランチャーログは、別途ハッシュで固定している。

凍結済みの V2 実行グリッドは全セルを完走した。10 セル中 10 セルが、引き続き実行上有効である。ここでいう実行上の有効性とは、各セルの凍結済み実行証拠が揃い、内部整合していることを指す。エンドポイント値や科学的成功を意味しない。

その後、分析器を 2 回起動した。どちらの起動でも、プログラムはラン配列を読み込んで検証したが、ランチャーログとの対応確認で停止した。エンドポイント構築にもブートストラップ計算にも到達せず、分析出力は生成されなかった。

プログラムが配列を読み込んだことと、人間が結果を見たことは同義ではない。2 回の失敗中、エンドポイント、対照統計量、区間、ブートストラップ値などの結果値は、人間向けに表示されておらず、人間も閲覧していない。

| 事象 | 状態 | 人間による結果値の閲覧 |
|---|---|---|
| 凍結済み V2 実行 | 10/10 セルが実行上有効 | 分析結果を意味しない |
| 分析器の起動 1 | エンドポイント構築・ブートストラップ前に停止 | 結果値の表示なし |
| 分析器の起動 2 | 同じ受け入れ確認で停止 | 結果値の表示なし |
| 修正方法の選定 | ソース上の制御フローとログ表示だけに基づく | メトリクス・結果による選定なし |

## 原因

非 TTY のランチャー出力では、Rich の表示幅が 80 列になっていた。そのため、`Complete` マーカーに続く長い実行ディレクトリパスが、物理ログ上の 2 行に折り返された。一方、既存の受け入れ確認は、折り返し前の期待パスを連続した 1 本のバイト列として検索していた。意味上は同じパスが記録されていても、Rich が表示用の改行を挿入した後には、そのバイト列は存在し得ない。

失敗箇所は、実行完了後かつエンドポイント構築・ブートストラップ計算前である。これはログ表示上の不一致であり、ラン配列の破損を示すものでも、実験仮説の当否を示す証拠でもない。

## この修正を採用できる理由

修正は、結果値を含まない次の 2 点だけから選んだ。

1. ソース上の制御フローから、エンドポイント構築とブートストラップより前に停止したと確認できること。
2. ランチャーログから、80 列幅の Rich 表示が完了パスを折り返したと確認できること。

修正の選定時には、メトリクス値、エンドポイント値、対照比較、保護バンクの内容、ブートストラップ結果を参照していない。修正版の分析を走らせる前に、この修正を凍結しなければならない。後から得られた結果値を理由に別の変更を加える場合は、新しいプロトコルとして明示し、本修正には含めない。

## 凍結する 2 行パーサー

この修正で認めるのは、次のパーサーだけである。汎用的なログ正規化は認めない。期待する解決済み実行ディレクトリパスを `P` とし、ランチャーログの全バイトと物理改行を保ったまま、次の契約を適用する。

```text
line[i]     = "Complete  "
line[i + 1] = fragment_1  # ちょうど 80 bytes
line[i + 2] = fragment_2  # 1..80 bytes
line[i + 3] = "{"         # 自動生成された最上位 report の開始
candidate   = fragment_1 + fragment_2
accept      iff exactly one marker-only line exists,
                candidate == P,
                basename(candidate) == expected_run_id, and
                neither P nor expected_run_id occurs as contiguous bytes
                anywhere in the raw log
```

2 つの断片は、空白やパス区切りを補わず、削らず、正規化せずに連結する。マーカーは独立した物理行である。どちらの断片も前後をトリムせず、マーカー直後の 2 行に連続していなければならない。ランチャーログ内のどこかに ANSI エスケープが 1 byte でもあれば、除去せず不合格とする。

次のいずれかに当てはまれば、パーサーは安全側で不合格とする。

- `Complete  ` だけからなる物理行が、厳密に 1 行ではない。
- 2 つのパス断片がマーカー直後の 2 行ではない、または、その次の行が厳密に `{` ではない。
- 第 1 断片がちょうど 80 bytes ではない、または第 2 断片が 1〜80 bytes ではない。
- 期待パスまたは期待 run ID が、折り返されていない連続バイト列として生ログ内のどこかに存在する。
- 復元したパスが、期待する解決済みパスと 1 文字でも異なる。
- 復元した basename が、期待する run ID と一致しない。
- 生ログ内のどこかに ANSI エスケープがある。
- いずれかの断片に空白、制御文字、非 ASCII 文字が含まれる。

basename だけの照合、部分文字列照合、曖昧照合、無制限の空白折り畳み、無制限の複数行連結、ファイルシステムからのパス探索は認めない。このパーサーが行うのは、あらかじめ期待値として与えられた 1 本のパスを、厳密な 2 行の表示レコードから復元することだけである。

パーサーの合格は、修正層における受け入れ判定にすぎない。その後、委譲先にある元の V2 来歴検証にもすべて合格しなければならない。どこか 1 か所でも失敗すれば、修正版の分析は不合格とする。

## 変更しない V2 証拠と数理

次の項目は、バイト単位で変更しない。

- 元の V2 ランチャーログと実行ディレクトリのすべて
- すべてのラン配列、レシート、run ID、行順序
- 元の V2 凍結マニフェストとそのダイジェスト
- 凍結済みの全設定と実験入力

エンドポイント定義、推定量、集約、対照、乱数 seed、ブートストラップ仕様、判定規則、報告ゲートを含む数理契約も変更しない。本修正を理由に V2 セルを追加・削除・並べ替え・修復・再実行してはならない。

## 追加する修正アーティファクト

実装は追加方式に限定する。修正層を構成するのは、次のアーティファクトだけである。

1. 英語版と日本語版を対にした本修正プロトコル
2. 本プロトコル、変更不能な V2 マニフェストのダイジェスト、マニフェスト自身を除く静的な修正ファイルすべてを結び付ける修正マニフェスト。後から生成する preflight レシートは、下流側の来歴情報で結び付ける
3. 厳密なパーサーとマニフェスト・preflight 検証を収めた、来歴検証用の共通 helper
4. エンドポイント構築やブートストラップを行わず、期待する 10 本のパスすべてを検査して修正 preflight レシートを公開する model-free audit
5. 修正後の受け入れ確認を行い、科学計算を凍結済みベース分析器へ委譲し、分析レシートに `analysis_validation_correction` の来歴情報を加える分析器アダプター
6. 同じ受け入れ修正を適用し、証拠検査と公開処理を凍結済みベース builder へ委譲し、root manifest に `post_execution_analysis_validation_correction` の来歴情報を加える bundle-builder アダプター
7. 変更不能なベース来歴、実際に使った修正層の来歴、委譲したベース validator の結果を検証する最終 validator アダプター
8. analyzer/audit 層と bundle 層に焦点を絞ったテスト

本修正のために、元の V2 ファイルを編集・置換・再生成してはならず、修正層のファイルを元の V2 ファイルと称してはならない。

## ベース実装と実際に使う実装の来歴

修正版の証拠系では、凍結済みのベース実装と、実際に呼び出した追加アダプターを明確に分ける。情報は、分析レシート、修正マニフェスト・preflight、公開用 root manifest に分けて、次のように記録する。

```text
analysis receipt
  analysis_implementation                 -> base analyzer {path, sha256}
  manifest_binding                        -> V2 freeze manifest {path, sha256}
  analysis_validation_correction.adapter  -> active analyzer adapter {path, sha256}
  analysis_validation_correction.manifest -> correction manifest {path, sha256}
  analysis_validation_correction.preflight-> correction preflight {path, sha256}

correction manifest / preflight
  scope.completion_parser_contract         = "rich_width80_exact_marker_plus_two_path_lines_v1"

root publication manifest
  tooling                                  -> base builder and validator
  post_execution_analysis_validation_correction.base_publication_tooling
                                           -> base builder and validator {path, sha256}
  post_execution_analysis_validation_correction.active_publication_tooling
                                           -> active builder and validator {path, sha256}
```

アダプターは、ベース実装を上書きしたり、ベース実装になりすましたり、ベース実装として報告されたりしてはならない。期待するハッシュ、パス、パーサー識別子、10/10 の preflight 結果、修正来歴ブロック、委譲したベース検証結果のいずれかが欠けるか一致しない場合、実際に使用する validator は bundle を不合格とする。

## 修正版分析の手順

1. 英日プロトコル、共通 helper/parser、audit、3 つのアダプター、焦点を絞ったテストを凍結してハッシュを記録する。その後、これらのファイルとベース V2 の authority を結び付ける修正マニフェストを凍結する。
2. 元の 10 本のランチャーログと、期待値として既知の 10 本の実行パスに対して修正 preflight を実行する。受理件数が厳密に 10 件で、曖昧性がない場合だけ通過とする。
3. 実際に使用するアダプターを介して分析器を実行する。表示層以外の検査と科学計算には、凍結済みベース実装をそのまま使う。
4. 実際に使用する bundle-builder アダプターを介して公開用の証拠 bundle を構築する。凍結済みベース builder へ処理を委譲し、root manifest に修正来歴ブロックを加えなければならない。
5. 実際に使用する validator を実行し、ベース実装と追加アダプターの来歴を識別できる検証 report を保存する。
6. ベース側と修正側の全検査に合格した場合だけ、公開用 bundle と結果の主張を公開する。

1 件でも失敗すれば、分析状態は invalid/incomplete のままとする。部分結果へ読み替えてはならず、primary status も公表しない。

## 主張境界

この実行後のパーサー修正で復旧できるのは、すでに凍結していた科学分析への経路だけである。研究設計の強度は上がらない。修正版の出力が得られても、凍結済み V2 ターゲット集合を対象とする、範囲を限定した探索的 transport 結果として扱う。

特に、tokenizer からの独立性、意味特異性、因果制御、機構、行動への転移、モデル間一般化、確認的な論文ゲートは示せない。10/10 は実行上の有効性だけを指す。audit が記録するのは、人間が閲覧した結果値に基づいてパーサーを選んだのではない、という範囲に限られる。V2 ターゲット集合が新たな holdout に変わるわけではない。

修正後の結果が正・帰無・混合・不確定のいずれに当たっても、同じ凍結済み規則で報告する。
