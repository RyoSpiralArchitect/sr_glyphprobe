# T13-EA ゼロゲート数値修正 v1

この文書は、T13-EA のゼロ対照ゲートに限った数値修正を凍結するためのものです。科学解析計画は変更しません。

## 修正が必要になった経緯

v0 の解析器は、Jensen–Shannon（JS）ダイバージェンスを含む4つのスカラー指標に厳密なゼロを求めていました。最初の実行では JS の検査で停止し、ゼロ以外の科学値は一つも開いていません。解析結果も書き出していません。この失敗は、手続き上の負の結果として `validation/emoji_steering_specificity_analysis_v0/zero_gate_v0_failure_receipt.json` に残します。

今回の修正に用いたのは、失敗した項目が JS だったという情報だけです。実データに残った差の大きさは確認しておらず、閾値の設定にも使っていません。

## 変更点

次の原始的な no-op 条件には、v1 でも厳密な一致を求めます。

- KL ダイバージェンス、全変動距離、ロジット差の RMS は厳密にゼロ
- 介入前後のエントロピーは厳密に一致
- 介入前後の argmax ID は厳密に一致し、語彙範囲内
- `argmax_flip` は false
- 正側上位値、負側上位値、CountSketch は厳密にゼロ
- 正側・負側の上位トークン ID は語彙範囲内

JS だけは別に扱います。JS は float32 の `log_softmax -> exp -> mean -> log` を経て得られる派生量です。入力ロジットが同一でも、`log(exp(logp))` が `logp` とビット単位で一致するとは限りません。そのため、有限かつ両側の残差について、次の上限を課します。

```text
abs(js_divergence) <= 8 * finfo(float32).eps
                   = 9.5367431640625e-07
```

これは、実装の演算経路から事前に定めた float32 の許容幅です。失敗時の実測値に合わせた閾値ではありません。JS は「float32 の往復演算で生じた派生残差」として記録し、厳密なゼロとは表現しません。

## 変えないもの

封印済みの実行データ、外部 closeout、6つの出力群、推定量、再標本化契約、対照条件、解釈上の制限はそのままです。解析器には、引き続き次の順序を課します。

1. 同じプロセス内で外部 closeout を再監査する。
2. 最初にゼロ対照の ledger と配列だけを開く。
3. 原始量の厳密検査と JS の上限検査をすべて通す。
4. ゲート全体を通過してから、ゼロ以外の科学値を開く。
5. 既存の解析出力を上書きしない。

どこか一つでも不合格なら、その場で停止します。

## 主張できる範囲

v1 の通過が示すのは、ゼロフック対照が「原始量では厳密な no-op であり、JS の派生残差も事前に凍結した float32 の上限内にある」という点だけです。科学的な効果を示すものではなく、科学的な帰無結果を修復するものでもありません。T13-EA の解釈範囲も広げません。

v0 の失敗と v1 の結果は分けて報告します。その後に科学結果が得られても、厳密一致ゲートが一度失敗した記録は残します。

## 凍結の境界

修正マニフェストは `data/manifests/emoji_steering_specificity_zero_gate_amendment_v1.json` に置きます。次のファイルを漏れなく結びます。

- v0 解析マニフェスト
- 検証済みの外部 closeout receipt
- v0 失敗 receipt
- 今回の設定ファイルと英日両方の文書
- v1 の geometry・outcome 解析ラッパーとそのテスト
- 修正監査器とそのテスト

マニフェストは、対象ファイルをすべて統合してから生成します。
