# 共通接頭列の採点整合性：8入力の診断

[English](CONTEXTUAL_EMOJI_PREFIX_CONSISTENCY_V0.md) · [背景と次の研究順序](CONTEXTUAL_EMOJI_MEASUREMENT_NEXT_PLAN_V0.ja.md)

2026-10-07（日本時間）。すでに観測した開発用入力に対する工学的診断である。ユーザーは次の研究順序に沿って進めることを承認した。本書では新しいモデルスコアを見る前に、最初の取得を **8つの入力×候補対、各7 forwards、最大56試行**に固定する。科学的標本の拡張、精度の総当たり、自動再試行、因果実験は含めない。

## 問い

保存スコアの監査では576入力×候補対のうち355で、A/Bの共通接頭列の対数スコア差が0でなかった。355例はすべて異長の520組に含まれ、等長の56組は差が0だった。同一の因果的履歴は数学的には同じ次token分布を定めるはずである。本診断では、モデル実行とスコア正規化の両方の形状をそろえると、記録されたBF16実装で共通部分の予測が一致するかを問う。

過去スコアの完全再現、同じ呼び出しの完全再現、形状をそろえた異なる候補間の共通接頭列一致を分ける。接頭列単独実行との形状間差は記述値として扱う。BF16の丸めと、あらゆるkernel・mask実装の選択をこの検査だけで切り分けることはできない。

## 対象を選ぶ固定規則

入力IDは `(pair_id, carrier, block_id, context, cue)` とし、通常のtuple辞書順を使う。保存済み解析のSHA-256は `806400d78608cc2999f9480d3b82b24a45fd4739f85f52d82a21f3f7cb4b39e8`。

1. original/emoji/affect_01、explicit_negation/emoji/affect_03、adjective_pair/emoji/thermal_04の各課題で、保存済み接頭列差の絶対値最大を選ぶ。同点ならID順。
2. 全取得済み入力で絶対差最大を選ぶ。同点ならID順。
3. 等長絵文字、等長単語、異長絵文字、異長単語の各層から、まだ選ばれていない辞書順先頭の入力を加える。
4. ID重複を除き、必要なら同じ4層を順に巡って未選択の先頭を加え、異なる8入力にする。選択理由と順序を保存する。

## 各入力×候補対につき7回

| 呼び出し | 実行 | 目的 |
| --- | --- | --- |
| 1–4 | 元のA、元のB、A再実行、B再実行 | 過去のtoken別・全文スコアとの完全一致、同じ呼び出しの再現 |
| 5–6 | A/Bを共通の最大長まで右padding | モデル形状、実token位置、スコア正規化形状をそろえる |
| 7 | prompt＋共通候補接頭列のみ | 別形状の因果的履歴との比較。厳密な正解と仮定しない |

元の呼び出しは、暗黙の位置指定、全要素1のpadding mask、KV cacheなし、eval/inference mode、候補長に応じた元のFP32正規化sliceを含め、記録済みforward引数を保つ。過去の全候補token対数確率と合計が完全に一致する必要がある。不一致なら取得を停止し、未実行の分母を残す。

padding実行では、有効なtoken ID 0を右padding位置だけに置き、実tokenを1・paddingを0とするmaskと明示的な絶対位置IDを使う。paddingは採点しない。両候補で同じ予測位置の長方形領域をFP32正規化した後、有効な候補スコアだけを取り出す。モデル入力長だけをそろえても、元の候補長sliceを保つと正規化計算の形状は異なるため、この区別が重要である。

各呼び出しで共通接頭列を予測するlogit tensorの形状・dtype・digestと、有効なtoken別対数確率・候補全体の合計を記録する。比較対象は共通候補tokenを予測する位置であり、共通列の最後のtokenも、その直前の履歴から予測する。logitの一致と、採点対象tokenの対数確率の一致を別々に検査する。

## 実行前に決める判定規則

- **過去との一致：** 元の呼び出しの全tokenスコアと合計が保存値と完全一致すること。新しい実行どうしの一致だけでは足りない。
- **元の実行の再現：** 各候補の元の呼び出し2回が完全一致すること。0以外の許容幅は設けない。
- **同一形状の接頭列：** padding後A/Bで、共通部分の予測logitのdigest・形状と、共通token対数確率列が完全一致すること。8組全体で判定し、不一致を失敗として残す。過去再現が通れば限定パネルを最後まで測り、通る例を探し直さない。
- **形状間比較：** 元・padding後・接頭列単独の差や候補スコア極性変化を、合否閾値なしで報告する。この結果からFP32や科学的効果への許容幅を後付けしない。
- **課題全体の科学的判定：** 評価不能。各課題の1入力からH、効果反転、全4入力一致は更新できない。全4入力が必要で、3課題だけでも12入力×候補対／84呼び出しに加えて別の対照が要る。

接頭列検査を通過しても、提案した採点形状を広く検証する候補にできるだけである。既存の科学的スコアを置換したり、1,248スコア全体を修復したとみなしたりはしない。mask・位置・padding・runtime・精度・採点形状を変える場合は新しい採点versionにし、該当する全セルを評価してから論文の数値を変える。

## 資源と出典の境界

既存のLlama 3.2 3B BF16ファイルと過去runtimeだけを使う。モデルmanifestは `dc5b61a2c4aa123f82e7d0471b4cdb3a7d8de3b6a8db327047fb1b6d05e3bdf4`。モデルdownload、量子化、学習、外部推論サービス、保護されたbankは使わない。

炉では独立したcheckoutを使う。割当前と毎forward直前にGPUのprocess・メモリを確認し、他GPU PIDや読めない占有状態があれば自分の取得を止める。他の実行を停止・変更しない。割当前に12 GiB、各forward前に4 GiBの空きを要し、allocator上限9,728 MiB＋driver許容量512 MiB、実行時間600秒を上限とする。これで実行を拒否しても、失敗後に上限を緩めない。占有確認は予約ではないため、確認間の競合は起こりうる。

入力・仕様・ソースのdigestを結び付け、JSON表現をそろえた過去のcore runtime全体と比較する。現在のmodel/maskソースファイルdigestは別に記録する。途中停止でも56の計画行IDを保つ。開始、runtime、占有、各呼び出し、完了を上書き不可で記録し、暗黙に再開しない。

## 解釈と次の一歩

同一形状の共通接頭列が一致すれば、形状をそろえた採点方式を、全開発セルで検証する具体的な候補にできる。診断パネル上では実行形状に関わる説明を支持するが、特定の算術kernelやdtypeの機構を同定するには追加検査が要る。

一致しなければ失敗を保存し、実際のlogit、mask、正規化経路を調べる。必要なら別予算のFP32比較を検討する。いずれの場合も、人によるラベル・候補検証、独立した課題確認、通常状態の因果検査は別段階として残る。
